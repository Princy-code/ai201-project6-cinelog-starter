## Comment 4 — Default visibility
**My position:** Keeping `public=True` as the default.

**Reasoning:** CineLog is described as a *community* film-tracking app — the whole point of the product is that other people can see what you're watching and want to watch. A private-by-default watchlist would work against that core use case for the common case: most users adding a film to their watchlist aren't doing so to keep a secret, they're doing it because they want to track and share what's next. Defaulting to public also matches the app's existing behavior — `CollectionEntry` (already-watched films) has no visibility flag at all, i.e., it's implicitly always visible — so a watchlist that defaults to public is the more consistent choice, not an outlier.

**Tradeoff acknowledged:** The real risk is a user who doesn't realize the default is public and adds something they'd rather keep quiet (an embarrassing title, a gift they're screening for someone, etc.) before they know the `public` flag exists. That's a real cost, not a hypothetical one. To address it without changing the default, I added the stretch feature that lets `public` be set explicitly on `add_to_watchlist()` (see the visibility toggle section below) — a client can prompt for visibility at add-time rather than the user having to discover the setting after the fact. A private-by-default sharing app also isn't especially social — I'd rather ship public-by-default with an easy opt-out than private-by-default with a feature nobody uses.

## Comment 5 — Sort order
**My position:** Pushing back — keeping alphabetical (`Film.title.asc()`) as the default rather than switching to date-added.

**Reasoning:** I'm not convinced "most users want to see what they added recently" holds for a watchlist specifically, the way it does for something like a notifications feed. A watchlist is a list you come back to when you're deciding what to watch next, often days or weeks after adding to it — at that point, "what did I add most recently" is not a distinguishing question, but "did I already add *this* title" or "let me scan for something I'm in the mood for" are. Alphabetical order directly supports both of those by making the list scannable and letting you jump straight to a known title, the same way you'd scan a bookshelf or a reading list.

There's also a consistency argument: alphabetical-by-title is already the sort order `films_bp.list_films()` uses for browsing all films (`Film.query.order_by(Film.title)` in `routes/films.py`) — it's the only other list-browsing endpoint in the app, and it establishes title-based ordering as CineLog's existing convention for "browse a list of films," as opposed to `get_collection()`, which sorts by `date_added` because a watched-history log is fundamentally chronological (you're recalling *when* you watched something) in a way a to-watch list isn't.

**Engagement with reviewer's point:** I don't think the "recently added" instinct is wrong so much as it's solving a real but different problem — knowing what you *just* added, which the `date_added` field already exposes per-entry for any client that wants to render "Added 3 days ago" or build a "recently added" view without changing the list's primary order. If usage data later shows people mostly interact with the watchlist right after adding to it (e.g., session-based add-then-browse behavior), that would be a concrete reason to revisit this — and at that point I'd suggest an optional `?sort=date_added` query param on `GET /watchlist/<user_id>`, following the same pattern `films_bp` already uses for `?genre=`/`?year=`, rather than replacing the default outright. I'm keeping the current default (alphabetical) and not implementing the query param now since it's speculative until there's a concrete reason for it.

## PR Description

**What this feature does:** Adds a watchlist to CineLog — a list of films a user wants to watch later, distinct from their collection (films already watched). A `WatchlistEntry` links a user and a film with a `date_added` timestamp and a `public` visibility flag. `POST /watchlist/<user_id>/add` adds a film (rejecting duplicates and nonexistent films), `GET /watchlist/<user_id>` returns the list sorted alphabetically by title, and `DELETE /watchlist/<user_id>/remove` removes an entry.

**Design decisions made:**
- **Default visibility (`public=True`):** Kept public-by-default since CineLog is a community app built around sharing what you're watching, and it's consistent with `CollectionEntry`, which has no visibility flag at all (implicitly always visible). The `public` field can be set explicitly on add to mitigate the risk of a user not realizing the default. Full reasoning in Comment 4 above.
- **Sort order (alphabetical by title):** Kept `Film.title.asc()` rather than switching to `date_added`, pushing back on the reviewer's initial preference. Alphabetical order makes the list scannable for "did I already add this" and matches the only other list-browsing endpoint in the app (`films_bp.list_films()`, also sorted by title), whereas `date_added` ordering makes more sense for `get_collection()`'s watched-history log, which is inherently chronological. Full reasoning and engagement with the reviewer's point in Comment 5 above.
